# Agent Harness 通用底座：全阶段落地执行方案

> **文档定位**：项目唯一执行蓝图，取代旧 PLAN.md 中的阶段安排
> **更新日期**：2026-07-18
> **适用对象**：CodeBuddy 自动化开发执行

---

## 核心原则

1. **ai-orchestration-service = 唯一 Agent 调度大脑**，Django 退化为纯工具/网关层
2. **底座无业务耦合**：所有业务能力通过 MCP 协议动态注入，底座代码不写死任何业务逻辑
3. **全链路 team_id 隔离**：工作流模板、工具可见范围、记忆命名空间、任务数据全部按团队隔离
4. **双接入模式**：大型业务远程 HTTP 调用，小型业务 SDK 本地嵌入

**总目标**：将 ai-orchestration-service 打造为企业通用 Agent Harness 底座，支撑多业务线（测试 / 财务 / 客服 AI）统一复用，对标「Agent Harness 架构师」岗位需求。

## 一、当前底座多业务适配能力评估

### 1.1 天然支持多业务的核心能力

| 能力 | 说明 |
|------|------|
| 调度完全解耦 | LangGraph 工作流、ReAct 循环、任务调度全部收敛至底座，Django 无调度代码 |
| MCP 标准化工具网关 | 任意业务可通过 MCP Server 注册自有工具，底座统一管控权限、审计、配额 |
| 原生 team_id 隔离 | 工作流模板、工具可见范围、向量记忆、任务数据全部隔离，天然支持多业务并行 |
| 通用底层能力 | Plan/Orchestrate/Verify 工作流、ReAct 循环、Checkpoint 断点续跑、Sandbox 沙箱、LLMRouter 多模型路由、三层记忆、全链路可观测 |

### 1.2 当前缺失项（补齐后满足通用底座标准）

1. 无底座独立可视化运维页面，无法直观管理多业务
2. ReAct 多轮智能体仅有骨架，未完成 LLM 端到端验证
3. 三层记忆仅有骨架，长期记忆未连 Milvus 真实读写
4. 缺少第二条模拟业务 Demo，无法直观证明多业务兼容能力
5. 无 Prometheus/Grafana 可观测体系

### 1.3 适配性结论

底层框架层面已具备多业务适配能力，缺失的是：可视化运维层、ReAct 真跑链路、多业务演示载体。补齐后可对标企业级通用 Agent Harness。

## 六、多业务适配强制开发规范

### 规范 1：业务零侵入原则

- 底座所有模块禁止硬编码测试业务相关逻辑
- 所有业务能力仅通过 MCP 工具动态注入
- 新增业务仅需实现 MCP 服务，无需修改底座内核代码

### 规范 2：数据隔离规范

- **底座存储**：全局调度、权限、记忆、任务数据，所有业务共享底座存储，依靠 team_id 做逻辑隔离
- **业务存储**：各业务独立自有数据库（测试平台 Django 库、客服业务自有库），业务库之间互不互通，仅通过 API 传递临时任务数据

### 规范 3：业务接入方式

外部业务接入底座仅支持两种标准方式：

1. **远程模式**：HTTP 调用底座 `/api/v1` 标准任务接口
2. **轻量化模式**：引入底座 SDK 本地内嵌

所有业务工具统一通过 MCP 协议注册，禁止自定义私有调用协议。

### 规范 4：租户隔离强制约束

- 所有任务、记忆、工具可见范围、工作流模板读写逻辑，必须携带 team_id 过滤条件
- 代码任何存储读写操作强制增加 team 隔离，杜绝多业务数据串扰

### 规范 5：底座与业务技术栈划分规范

1. 通用 Agent Harness 核心底座 `ai-orchestration-service` 固定采用 Python FastAPI，禁止切换 Java；
2. Django 仅作为 AI 测试业务层网关，仅处理测试业务资产，不承载任何智能体调度核心逻辑；
3. Java 仅可用于开发演示用第三方业务 Demo（模拟客服系统），仅用来验证底座多语言业务接入能力，不作为底座主体；
4. 所有 Agent、MCP、记忆、沙箱、工作流相关开发统一在 FastAPI 底座工程内维护，业务层不得复制、重写同类底层逻辑。

- 所有任务、记忆、工具可见范围、工作流模板读写逻辑，必须携带 team_id 过滤条件
- 代码任何存储读写操作强制增加 team 隔离，杜绝多业务数据串扰

## 附录 A：面试话术模板

### 为什么统一大脑？

> "早期项目里为了快速验证，Django 内和独立编排服务各写了一套 Harness。后续我把它统一成单一大脑，Django 只当工具层。这样设计是为了 SaaS 化：每个团队可以有自己的工作流模板、私有工具、独立记忆和模型偏好，平台去适配团队，而不是让团队适配平台。"

### 底座 vs 测试平台的定位

> "整体项目建设我采用分层落地思路，优先投入全部资源搭建通用 Agent Harness 底座，底座是全公司 AI 业务可复用底层基建，是整套方案核心价值。当前 AI 测试平台仅作为底座首个落地验证业务载体。对标成熟商用测试平台后，我梳理出知识库、自动化流程、资产治理等优化点，规划在底座完全稳定、具备完整多业务适配能力后，再迭代完善上层测试业务平台，优先保障底层通用架构的完整性与通用性。"
