## 1. 为什么做两套 Harness？

**没有合理业务理由，是历史技术债务。**

- `backend/core/agents/harness/workflow.py`：Django 进程内版，最早为 MVP 直接写在里面。
- `ai-orchestration-service/app/core/workflow.py`：独立编排服务版，后来想解耦 Web 请求和 Agent 编排。

结果两套各写了一半，都没做完。

---

## 2. 现在方案：统一还是打通？

**统一成单一大脑，不是打通两套。**

- 保留 `ai-orchestration-service` 为唯一 Agent Harness 大脑。
- Django 退化为工具/网关层，只暴露 Agent 工具 API。

### 企业架构视角

| 层级 | 职责 | 归属 |
|------|------|------|
| 编排平面 | Plan / Orchestrate / Verify / ReAct / Checkpoint / Memory | `ai-orchestration-service` |
| 工具平面 | 用例生成、执行、评估、知识库等 | Django + MCP/ToolGateway |
| 团队平面 | 各团队自己的工作流模板、私有工具、记忆命名空间、模型偏好 | 通过 `team_id` 隔离 |

**核心原则**：平台提供积木，团队自己拼。平台适配团队风格，不是团队削足适履适配平台。

### 面试话术

> “早期为了快速验证，Django 内和独立编排服务各写了一套 Harness。后续我统一成单一大脑，Django 只当工具层。这样设计是为了 SaaS 化：每个团队可以有自己的工作流模板、私有工具、独立记忆和模型偏好，平台去适配团队，而不是让团队适配平台。”

## 3. 不是只有 DeepSeek 和 Qwen 吗？需要两套 Harness 才能调用？

**不需要。模型数量 ≠ Harness 数量。**

一套 Harness 里可以通过 LLM Router / Provider 同时调用多个模型：

```python
router = get_llm_router()
response = router.chat(messages, task_type="planning")
```

底层根据配置切到 DeepSeek、Qwen、OpenAI 都可以。两套 Harness 是为了“编排放在哪一层”的问题没想清楚，不是为了模型。

## 4. 多轮思考 ToolCall 循环在哪里实现？

**现在没实现**。当前工作流是“一次性计划 → 执行 → 验证”的批式流水线。

真正的 ReAct / ToolCall 循环会加在 `ai-orchestration-service/app/core/workflow.py` 里，变成：

```
[reason] → LLM 思考 → 需要工具？
  │ 是                    │ 否
  ▼                       ▼
[tool_executor]      [verify]
  │                       │
  ▼                       ▼
[reason] ◄────────── [END]
```

- `reason`：LLM 根据当前 state 决定下一步动作。
- `tool_executor`：调用 MCP/Agent 工具。
- 条件边：如果 LLM 返回 `tool_calls`，就回到 `reason`；否则去 `verify`。

## 5. 长期记忆：全通用还是个别功能？

**方案：先做通用记忆层，再按功能打标签。**

```python
class MemoryManager:
    def add(user_id, task_type, content, tags=[])
    def retrieve(user_id, query, tags=[], top_k=5)
```

- **通用层**：所有 Agent 都通过 `MemoryManager` 读写。
- **功能标签**：`testcase_gen`、`chat_history`、`execution_result`、`user_preference`。

前期先做 `chat_history` 和 `testcase_gen` 两个高频功能，跑通后再扩。

## 6. 断点续跑（Checkpoint）是什么意思？

LangGraph 的 Checkpoint：每执行完一个节点，把完整 `state` 快照存下来。

```python
state = {
    "user_request": "...",
    "plan": [...],
    "current_step": 2,
    "results": [...],
    "context": {...},
}
```

执行到 `orchestrate` 节点后，把 state 完整写入 Redis/Postgres。服务重启后加载最新 checkpoint 继续执行。

### 和现有 WorkflowProgress 的区别

| 能力 | WorkflowProgress（现状） | Checkpoint（目标） |
|------|------------------------|------------------|
| 存什么 | 进度/状态/事件 | 完整 state 快照 |
| 能恢复吗 | 只能看到“跑到第几步” | 能恢复到具体节点继续跑 |
| 重启后 | 流程丢失，从头跑 | 从断点继续执行 |

### 面试话术

> “Agent 编排是长流程，可能跑几分钟。如果服务重启，没有 Checkpoint 就要从头跑，用户体验很差。我们引入 LangGraph Checkpoint，把每个节点执行后的完整状态持久化到 Redis，重启后加载最新 checkpoint 继续执行。”

## 7. 自愈工作是什么意思？

**自愈 = Agent 执行失败后自动诊断、自动修复、自动重试。**

### 没有自愈

- LLM 返回格式不对 → 直接报错 → 人工重试
- 网络超时 → 直接报错 → 人工重试
- Agent 内部逻辑问题 → 直接报错 → 人工排查

### 有自愈

```
Step 失败
  │
  ▼
ErrorClassifier.classify(error)
  │
  ├─ fixable=false → 放弃，返回原始错误
  │
  ▼ fixable=true
SelfHealingEngine.heal()
  │
  ├─ RetryWithBackoff      → 网络/超时/LLM → 最多重试 3 次，指数退避
  ├─ AIFixSyntax (失败后)   → 语法错误     → LLM 修复后重试
  └─ AIDiagnose  (最后)    → 未知错误     → LLM 诊断 + 建议参数后重试
  │
  ▼
  healed → 返回成功结果
  失败   → 返回原始错误
```

### 面试话术

> “Agent 执行链路长，LLM 不稳定、网络抖动都会导致单步失败。我们做了自愈引擎，通过错误分类 + 策略链（重试/LLM修复/LLM诊断）自动恢复，减少人工介入，提高整体成功率。”

## 8. 工作流模板注册表是什么？

**模板不是替代 LLM Plan，而是给 LLM Plan 一个可信的骨架。**

### 现状问题

- 每次 `PLAN_SYSTEM_PROMPT` + LLM 实时生成计划，同一个需求两次跑结果可能完全不同
- 团队 A 想用 `generator→data_factory→execution`，团队 B 想用 `data_factory→generator→execution→evaluator`，做不到
- 工具注册只是字符串映射 `{"generator": "generate_testcases"}`，没有参数 schema 约束

### 模板设计

```python
WorkflowTemplate:
  template_id, team_id, version, status
  model_preference          # 该团队偏好的模型
  steps: [
    WorkflowStep(order, agent, prompt_template, params_schema, parallel_group, timeout, retry)
  ]
```

- 每个 `team_id` 可有多个模板，有一个默认模板
- Plan 阶段：查模板 → 模板骨架 + LLM 填充参数 → 执行
- 无模板时回退 LLM 自由生成（向后兼容）
- 存储：先 Redis（JSON），以后切 Postgres

### 面试话术

> "编排服务不只是每次让 LLM 自由发挥，我们设计了团队级工作流模板注册表。每个团队可以注册自己的流水线模板，LLM Plan 阶段在模板骨架的约束下填充参数，保证流程一致性的同时保留灵活性。"

## 9. 本地代码沙箱怎么设计？（本地起步，不上来就 Docker）

**不是上来就 Docker 容器，企业里也是本地跑通再上服务端。**

### 三层架构

| 层 | 职责 | 本地实现 | 服务器升级 |
|----|------|----------|-----------|
| FileJail | 文件隔离 | 临时目录拷贝 + 只读 | Docker volume + read-only mount |
| ResourceLimiter | 资源限制 | psutil 监控 + 超限 kill | cgroups |
| ProcessManager | 进程管理 | subprocess.Popen + timeout watchdog | Docker exec + stop |

### 核心策略

```
1. SandboxConfig(超时/内存上限/CPU限制/网络开关)
2. SandboxExecutor.execute(code) → SandboxResult(状态/耗时/峰值内存/输出)
3. 本地版：subprocess + psutil，Windows 兼容
4. 服务器版：同一套接口，底层切 Docker
```

### 面试话术

> "AI 生成的测试代码不能直接在宿主机上跑。我们做了一层沙箱执行器，本地版用 subprocess + psutil 做进程隔离和资源限制，文件操作限制在临时目录里。关键设计是本地和服务器用同一套接口，换底层实现不改业务代码。"

## 11. 沙箱 = 黑客帝国里的 Construct（虚拟训练场）

**本质**：AI 生成的代码不可信，不能直接在宿主机跑 → 给它一个受控的"训练场"。

| 阶段 | 黑客帝国内 | 沙箱实现 |
|------|-----------|----------|
| 训练场 | Construct 程序（白色房间） | 临时目录 C:/Temp/sandbox_xxx |
| 规则限制 | 物理规则可控 | 内存上限、CPU 限制、超时 kill |
| 失败了 | 不会真死 | 删临时目录，不影响宿主机 |
| 练好了 | 进母体实战 | 服务器用 Docker 容器跑真实测试 |

三层机制：
1. **FileJail**（文件监狱）→ 工作目录锁定在临时文件夹
2. **ResourceLimiter**（资源守卫）→ psutil 后台监控，超限一刀切
3. **ProcessManager**（进程管理）→ subprocess + timeout，到点就杀

## 12. 工程踩坑记录

### 12.1 PowerShell 中文乱码（UTF-8 BOM）

**现象**：Windows 下 `.ps1` 脚本里中文注释变乱码，PowerShell 右键运行报错。

**根因**：PowerShell 5.x 默认按系统 ANSI 编码（GBK）读脚本，UTF-8 without BOM 的文件会被误解析。

**修复**：用 `utf-8-sig` 保存，给文件头加 BOM 标记。

**教训**：Windows 项目里所有 `.ps1` 脚本统一用 UTF-8 with BOM 保存。

### 12.2 API Key 泄露到 Git 历史

**现象**：`.env` 里硬编码了 DeepSeek API Key，早期 commit 里已经包含，仓库公开后泄露。

**修复流程**：
1. 立即在 DeepSeek 后台重置 Key（先止血）
2. `git filter-branch` 清理历史
3. 强制推送覆盖远程
4. 清除本地 reflog

**教训**：项目启动前写好 `.gitignore`，Key 永远走环境变量。公开仓库一旦泄露，重置 Key 是唯一可靠方案。

### 12.3 `.env.example` vs `.env` 边界

- `.env.example`：提交到 Git，放占位符
- `.env`：永远不提交，放真实值
- `docker-compose.yml` 用 `${VAR:?error_msg}` 占位，启动时没设变量直接报错

### 12.4 Celery Windows 兼容

Celery 4.x+ 官方不支持 Windows worker。开发用 `eventlet` 协程池代替 prefork，生产走 Docker Linux worker。

### 12.5 Docker Compose 服务启动顺序

`depends_on` 只等容器启动，不等服务就绪。PostgreSQL 容器起来了但没准备好连接，Django migration 就报错。修复：加 `condition: service_healthy` + healthcheck + 启动脚本里 retry 等待。

### 12.6 Milvus 向量维度不匹配

换 embedding 模型后（如 768→1024 维），已有 collection 维度不匹配。Collection 创建时固化维度，改模型需重建。生产环境 embedding 模型不要轻易换，加版本标记。

### 12.7 LLM 返回 JSON 不稳定

要求返回 JSON 但 LLM 经常多打 markdown 包裹或漏逗号。兜底方案：直接解析 → 去 markdown 包裹再解析 → 交给 LLM 修复（三级降级）。

### 12.8 LangGraph Checkpoint 序列化

state 里有 `datetime`/`Decimal`/自定义对象时默认 serializer 炸。方案：自定义 serializer，`default=str` 兜底。

## 13. 架构选型对比速查

| 决策点 | 选了 | 没选 | 原因 |
|--------|------|------|------|
| 后端框架 | Django + FastAPI 双架构 | Flask / 纯 FastAPI | Django admin + ORM 成熟；FastAPI 适合 Agent 异步编排 |
| Agent 编排 | LangGraph | 自研 / CrewAI / AutoGen | Checkpoint 原生支持 + 社区生态，比 CrewAI 灵活 |
| 向量数据库 | Milvus | Pinecone(收费) / Chroma(单机) | 开源免费 + 分布式 + 混合检索 |
| 任务队列 | Celery + Redis | Dramatiq / RQ | Django 集成最成熟 |
| 前端 | Vue 3 + Vite | React | 对新手友好，学习曲线平 |
| 容器化 | Docker Compose | K8s | 早期 1-2 台机器，K8s 过重 |
| LLM Provider | DeepSeek + 多模型路由 | 单模型绑定 | 单模型不可靠，cost/quality tradeoff |
