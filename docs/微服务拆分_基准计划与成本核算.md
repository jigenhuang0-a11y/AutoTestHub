## 一、阿里云微服务环境分析

### 阿里云有什么？

| 产品 | 用途 | 是否适合你 |
|------|------|-----------|
| **MSE (微服务引擎)** | 全托管 Nacos/ZooKeeper 注册中心 + 配置中心 + 网关 | ✅ 适合，但贵 |
| **ACK (容器服务)** | K8s 集群，管理多微服务容器 | ❌ 过重，一个人用不着 |
| **SAE (Serverless应用引擎)** | 免运维的微服务部署 | ✅ 轻量，但绑定阿里生态 |
| **函数计算 FC** | 按调用付费，Agent可做成函数 | ⚠️ LLM调用延迟大，不适合 |
| **API网关** | 统一入口、限流、鉴权 | ✅ 适合暴露给前端做统一入口 |

### 核心结论：MSE太贵，个人项目不需要

MSE Nacos 专业版 1核2G **209元/月**，这只是注册中心的钱，还没算服务器。而且你的微服务就 2-3 个实例，用不上全托管。

**你的最佳策略：Docker Compose 自建 Nacos + 服务发现，零额外成本。**

## 二、微服务拆分架构图

```
                    ┌─────────────────────────────┐
                    │      前端 (Vue 3)           │
                    └─────────────┬───────────────┘
                                  │ HTTP/SSE
                    ┌─────────────▼───────────────┐
                    │   API Gateway (Nginx)        │
                    │   统一入口 / 反向代理 / 限流   │
                    └──┬──────────────┬────────────┘
                       │              │
         ┌─────────────▼──┐    ┌──────▼──────────────────┐
         │ Django 业务服务  │    │ AI编排服务 (FastAPI)      │
         │  - 项目管理      │    │  - Harness 工作流引擎     │
         │  - 用户管理      │    │  - 5个Agent (Plan等)     │
         │  - 用例管理      │◄──►│  - 工具层调度             │
         │  - 报告管理      │REST│  - SSE流式进度推送        │
         │  Port: 8000     │    │  Port: 8001             │
         └────────┬────────┘    └───────────┬─────────────┘
                  │                         │
                  ▼                         ▼
         ┌───────────────────────────────────────────────┐
         │              共享基础设施 (Docker Compose)       │
         │  ┌──────────┐  ┌──────────┐  ┌─────────────┐  │
         │  │PostgreSQL│  │  Redis   │  │ Nacos (可选) │  │
         │  │  :5432   │  │  :6379   │  │   :8848      │  │
         │  └──────────┘  └──────────┘  └─────────────┘  │
         └───────────────────────────────────────────────┘
```

**关键设计决策：**
- Django 和编排服务**共享同一个 PostgreSQL**，避免数据同步问题
- Redis 做编排服务的运行时状态缓存（当前步骤、中间结果）
- Nginx 统一入口，前端只看到一个地址
- 两个服务相互独立部署，互不阻塞

## 四、成本核算

| Redis (Docker) | 运行在轻量服务器内 | 免费 | 0 |
| **合计** | | | **~240元/月** |

## 六、为什么拆分是你最大的筹码（面试核心逻辑）

### 面试官的决策瓶颈

面试官真正纠结的不是"你会不会写代码"——是"你来了我们公司能不能干活"。

| 他看到的信息 | 他的顾虑 | 他的行动 |
|-------------|----------|----------|
| 你会搭AI测试平台 | ✅ 能力不错 | 先标记，再看几个 |
| 但是单体结构 | ⚠️ 我们是微服务体系 | 等更匹配的 |
| 你没做过架构演进 | ⚠️ 从原型到生产要多久？ | 不确定，再观望 |

**他没办法下定"就是他"的决心，因为有一个关键验证缺失了。你做微服务拆分，就是提前把这个验证补上。**

### 拆分后的面试杀伤链

面试官问："你一个人做的？" → 你答："是。而且我后来把AI编排层从单体拆出来做了微服务。"

**这一句话改变的是什么：**

| | 拆分前 | 拆分后 |
|---|---|---|
| 他能确定的事 | 你会写 Django | 你会写 Django + 你会做架构决策 |
| 他对适配性的判断 | "不一定能融入我们体系" | "这个人自己踩过拆分的坑" |
| 他对你定位的判断 | 中级开发 | **能做微服务架构的AI应用工程师** |
| 薪资锚点 | 跟着市场走 | **稀有组合，溢价空间** |

### 面试话术（"为什么拆微服务"这个问题）

> "拆微服务不是因为单机跑不动，是考虑到真实企业的部署场景。我们平台如果进企业，AI编排层必须独立部署——业务量波动时跟Django的解耦是一个硬需求。所以我提前做了这个验证，证明这个平台不仅能在单体原型上跑通，也能直接融入企业现有的微服务体系。"

**暗中传递的信息：**
- 不是"只会写代码"——会做架构判断
- 不是"等别人安排"——提前验证企业的真实需求
- 不是"理想化"——已经在企业约束条件下落地过
